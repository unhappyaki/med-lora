## 3. 扩展 Gold 审计发现

固定 50 条 holdout 中共有 9 个 Gold 值以 `医师`、`某某医师` 或断行后的 `主治\n医师`结尾。这些均应按签名边界统一处理，不能只修本轮预测恰好漏掉的 4 条，否则会形成 prediction-driven relabeling 偏差。

另有 1 条 `中医辨病辨证依据` Gold 内嵌明确的同级标题“西医辨病辨证依据与鉴别诊断”，只是标题被换行拆成“西\n医…”，旧 relabeler 未识别。应拆为：

- `中医辨病辨证依据`：只保留中医段落；
- `诊断依据`：从“西医辨病辨证依据与鉴别诊断”标题后开始，到下一个同级标题前结束。

## 4. 另外两个推理侧问题

1. 一条首次病程的鉴别诊断正文含英文双引号（如 `"C"形`、`"咖啡豆征"`），模型生成时转义损坏，JSON repair 将该 item 修成了错误对象，最终产生 `invalid_item:3`。这是**引号转义/JSON 稳定性**问题。
2. 一条诊疗计划只改变了 `1\n、` 的空白位置，严格 grounding 将整字段删除。已增加“唯一空白归一匹配后映射回原文连续子串”的保守恢复规则；仅在归一文本长度至少 8 且全文唯一命中时启用。
3. chunk fallback 已增加“同一规范字段最多保留一次”的合并约束，避免年龄、记录者被多个 chunk 重复合并。

## 7. 84 秒推理耗时诊断

对同一条冒烟样本做分段计时后，确认慢点主要在长输出的自回归解码，不在数据读取、SSH 或 checkpoint 复制：

- tokenizer 加载：约 `0.82s`；
- 基础模型加载：约 `4.14s`；
- LoRA 挂载并迁移到 GPU：约 `1.22s`；
- 输入 Prompt：1700 tokens；
- 输出：1223 tokens；
- 预热后 128-token 基准：约 `17.2–17.7 tokens/s`；
- 生成阶段 GPU 平均利用率约 14%，平均功耗约 90W，显存约 2.4GB。

按 `1223 / 17.5 ≈ 70s` 估算，绝大多数时间都用于逐 token 输出多个长 Section；再加约 6 秒冷启动、首 token 预填充、解码和评测落盘，得到约 84 秒的端到端耗时。模型使用 BF16、CUDA、KV cache，未发生 CPU 推理或显存不足。

Qwen3.5-0.8B 是 24 层混合结构，其中 18 层 linear attention、6 层 full attention。容器已安装 FLA 和 causal-conv1d 内核；基础模型当前瓶颈是 Transformers 下 batch=1 的串行解码和超长逐字输出，无法靠移动数据目录解决。后续严格对照进一步确认，PEFT 动态 LoRA 的计算量虽小，但大量逐 token 小 kernel 调度会成为主要额外开销，详见第 9 节。

优化优先级：

1. 模型常驻服务，先消除每次约 6 秒冷启动；
2. 端到端批量评测采用连续 batching，而不是逐病例启动进程；
3. 使用 vLLM/SGLang 等推理引擎做动态批处理，但需先补齐匹配的 FlashInfer kernel 运行环境；
4. 若业务允许，改为输出原文字符区间而非逐字复制长正文，速度提升最大；若控件必须直接拿全文，则不能使用这一项；
5. 不建议为了速度截断 `max_new_tokens`，会重新引入“病历特点末尾少拷贝”。

## 9. 动态 LoRA 推理性能根因与修复

用户反馈“微调前输出很快”后，使用同一 1700-token Prompt、固定生成 128 tokens 对基础模型、PEFT 动态 LoRA 和合并 LoRA 做严格对照：

| 运行方式 | 两次稳态速度 |
|---|---:|
| 基础模型 | 34.77 / 30.94 tokens/s |
| PEFT 动态 LoRA | 18.39 / 18.06 tokens/s |
| `merge_and_unload` 合并 LoRA | 33.02 / 35.30 tokens/s |

V13.1 adapter rank 为 16，覆盖 `q/k/v/o_proj`、MLP、GDN 等 12 类 target module。动态 PEFT 在每个解码 token、每个目标层都额外执行低秩矩阵运算和 kernel 调度，使速度下降约 45%–48%。合并耗时仅约 0.105 秒，动态和合并模型生成的 128 个 token 完全一致。

已完成修复：

- 9876 工作台启动时把 adapter 加载到 GPU 后执行 `merge_and_unload(safe_merge=True)`；
- `/health` 后端标识为 `transformers-merged-lora-persistent`，并返回 `adapter_merged: true`；
- `evaluate_v5.py` 默认合并 adapter；保留 `--keep-adapter-unmerged` 作为诊断开关；
- grounding 4/4 回归测试继续通过。

端到端复测：

- 合成首次病程：82 输出 tokens，6.17 秒降至 3.65 秒；字段和质量状态完全一致；
- 原 1223-token 真实 holdout：84 秒降至 35.12 秒，`34.83 tokens/s`；
- 真实 holdout 的 TP/FP/FN 仍为 4/2/1，F1 `0.727273`；strict JSON、Schema、grounding 均通过，无 repair、验证错误或 token 截断。

结论：本轮主要性能问题不是 4090、数据位置或微调权重本身，而是生产推理仍以 PEFT 动态 adapter 运行。推理阶段合并权重后恢复到基础模型同档速度，长样本端到端约提升 2.4 倍。

### 11.3 本轮问题与原因

1. FlashInfer sampler 在当前 CUDA 环境没有匹配的预编译内核；通过 `VLLM_USE_FLASHINFER_SAMPLER=0` 使用 PyTorch sampler，注意力仍使用 FlashAttention 2，GDN 仍使用 Triton/FLA。
2. 首次 vLLM 尝试缺少 `ninja`，无法完成 JIT；在 py312 环境安装 `ninja 1.13.2` 后恢复。
3. `merge_and_unload().save_pretrained()` 只保存权重和 tokenizer，vLLM 按 Qwen3.5 多模态架构初始化时还需要 `preprocessor_config.json`、`video_preprocessor_config.json`、`merges.txt` 和 `vocab.json`；从基础模型补齐非权重处理器文件后加载成功。
4. 动态 LoRA 的 128-token 首请求只有 63.35 tok/s，原因是日志明确显示首次请求触发 `_lora_expand_kernel` JIT；长输出摊薄一次性抖动后达到 285.05 tok/s。离线合并模型消除了该 LoRA kernel 路径并提高到 302.60 tok/s。
5. 远端 30010 SSH 映射在部署期间存在间歇性 banner timeout/connection closed；已有 9876 服务和模型进程未中断。采用幂等启动脚本、PID 文件、端口检查、远端语法检查和健康检查，避免重复拉起或误杀稳定服务。
6. 9876 原启动参数把 HTTP keep-alive 设为 300 秒，切换后端时 Uvicorn 会长时间等待浏览器连接关闭；部署时发送第二次中断完成切换，并把后续启动参数降为 30 秒。该参数只控制空闲连接复用，不会截断最长 600 秒的后端推理请求。
